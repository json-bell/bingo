# Backend architecture

Why this exists: `docs/plan.md` sketched a "future SQL migration shape" as a maybe. This doc
is that shape actually decided — the schema, the routes, the local/test/prod database setup,
and the offline-write design that replaces `src/lib/checked.ts`'s localStorage backing. It's
the counterpart to `.claude/rules/architecture.md` (which covers the frontend/generator side)
and supersedes `docs/plan.md`'s "Future SQL migration shape" and "Checked-state roadmap"
phases 2/3, which were explicitly labelled sketches-not-commitments there.

Scope in one line: **the database stores one mutable boolean per grid cell, and nothing
else.** Grid content — every `BingoItem` field, the 5×5 layout, which person owns which grid
— stays exactly where it is: static `grids/<slug>/<n>.json` files generated by
`npm run make-grid`, promoted by editing `config/trips.json`'s `currentVersion`. This was
decided deliberately and is not a stepping stone: grid content is immutable once generated
and already well-served as cacheable static chunks (see `vite.config.ts`'s `trip-data/` lane).
There is no `cells` table with denormalized summary/description text, now or later.

## 1. Stack

| Concern | Choice | Why |
| --- | --- | --- |
| Database (prod) | **Neon** serverless Postgres, free tier | Scales to zero instead of *pausing* a project after N days of inactivity. This app is used hard for one weekend a year and ignored the rest — a cold start on the first request is completely acceptable; a suspended project that needs manual reactivation is not. |
| Backend code | **Vercel Functions** in a top-level `api/` directory, same repo | One deploy target, one set of env vars shared with the frontend, same origin so there is no CORS config to get wrong, and no second repo/pipeline to keep in sync with `types/trip.ts`. |
| Query layer | **Drizzle ORM** (`drizzle-orm` + `drizzle-kit`) | Typed queries against the same TypeScript the rest of the repo is written in, generated SQL migration files checked into git (the only durable record of schema history, since there's no CI), and first-class support for Neon's HTTP driver. |
| Local dev DB | **Docker Postgres** via `docker-compose.yml`, `DATABASE_URL` in a gitignored `.env.local` | Works offline, costs nothing, resets in seconds. Not a hosted Neon dev branch — that would make the local loop depend on network access, which is exactly the thing this app is built to tolerate losing. |
| Test DB | A **second database on the same container** (`bingo_test`), truncated between tests | No Testcontainers, no per-test container spin-up cost. One `docker compose up -d` covers both dev and test. |
| CI | **Deliberately skipped** | Solo project; tests already run before every commit in this workflow. The one thing CI would genuinely add — proving migrations apply to a truly clean database rather than a locally-drifted one — isn't worth the setup yet. Revisit if the backend grows more moving parts or gains contributors. |

### Driver split (the first real gotcha)

Neon's HTTP driver and a plain TCP Postgres connection are **not interchangeable**, and the
local Docker container speaks only the latter:

- **Production (Neon)**: `drizzle-orm/neon-http` + `@neondatabase/serverless`. Stateless
  HTTP-per-query, which is what you want in a serverless function — a `pg` connection pool in
  a Vercel function leaks connections across cold starts and will exhaust Neon's free-tier
  connection limit.
- **Local dev + tests (Docker Postgres)**: `drizzle-orm/node-postgres` + `pg`. Neon's HTTP
  driver cannot talk to a plain Postgres server at all — it needs Neon's HTTP proxy in front.

Drizzle's query-builder API is identical across both, so **only the client construction
differs** — every query, the schema, and all route code are driver-agnostic. Select the
driver from an explicit env var, not by sniffing the connection string:

```ts
// db/client.ts
import { drizzle as drizzlePg } from "drizzle-orm/node-postgres";
import { drizzle as drizzleNeon } from "drizzle-orm/neon-http";
import { neon } from "@neondatabase/serverless";
import { Pool } from "pg";
import * as schema from "./schema";

const connectionString = process.env.DATABASE_URL;
if (!connectionString) throw new Error("DATABASE_URL is not set");

// Explicit, not inferred from the hostname: "does this URL look like Neon?" is a
// guess that breaks the day a connection string format changes. DB_DRIVER is set
// once in the Vercel dashboard and never again.
export const db =
  process.env.DB_DRIVER === "neon"
    ? drizzleNeon(neon(connectionString), { schema })
    : drizzlePg(new Pool({ connectionString }), { schema });
```

`neon-http` **cannot run multi-statement transactions**. Nothing here needs one — every write
is a single-row conditional update and seeding is a single multi-row `INSERT` — but don't
reach for `db.transaction()` in a route without checking this first.

### Where the files live

`db/schema.ts` and `db/client.ts` sit at the **repo root**, not inside `api/` — deliberately
mirroring `types/trip.ts`. Both `api/` (the routes) and `data/` (the `make-grid` seeding step)
import them, and a shape imported by two contexts belongs at the root in this repo, same
argument as the `BingoItem`/`GridCell` types.

```
db/
  schema.ts          # Drizzle table definitions
  client.ts          # the driver-switching db export above
  migrations/        # drizzle-kit generate output — committed
drizzle.config.ts    # points drizzle-kit at db/schema.ts + db/migrations
api/
  health.ts                    # GET /api/health
  health/db.ts                 # GET /api/health/db
  checked.ts                   # PATCH /api/checked
  trips/[slug]/checked.ts      # GET /api/trips/:slug/checked
  lib/responses.ts             # shared json()/error() helpers — the status contract
  test/setup.ts                # Vitest setup for the api project
data/
  seedGrid.ts                  # seedGrid() — called by createGrids.ts and the CLI below
  seedGridCli.ts               # npm run seed-grid -- <slug> <version>
docker-compose.yml
```

## 2. Schema

### The `checked` table

```ts
// db/schema.ts
import { boolean, index, integer, pgTable, text, timestamp } from "drizzle-orm/pg-core";

export const checked = pgTable(
  "checked",
  {
    // GridCell.id — a crypto.randomUUID() minted at placement time in
    // data/getGrids.ts's makeGrid(). Stored as text, not uuid: it's an opaque
    // join key that the app never parses, and text keeps it trivially
    // comparable to the string sitting in grids/<slug>/<n>.json.
    cellId: text("cell_id").primaryKey(),
    checked: boolean("checked").notNull().default(false),
    // Server-authoritative. Every successful write sets this to NOW() — see
    // the PATCH contract in §4. The client never chooses this value.
    updatedAt: timestamp("updated_at", { withTimezone: true })
      .notNull()
      .defaultNow(),

    // Scoping columns — NOT part of the key, and NOT cell content. See below.
    tripSlug: text("trip_slug").notNull(),
    gridVersion: integer("grid_version").notNull(),
    person: text("person").notNull(),
  },
  (table) => [index("checked_trip_idx").on(table.tripSlug, table.gridVersion)]
);

export type CheckedRow = typeof checked.$inferSelect;
export type NewCheckedRow = typeof checked.$inferInsert;
```

**`cell_id` alone as the primary key is correct — verified.** `makeGrid()` in
`data/getGrids.ts` assigns `id: crypto.randomUUID()` per *placed* cell (line 89), not per
source `BingoItem`, so the same CSV row appearing in nine people's grids produces nine
distinct ids. Confirmed against the live data: `grids/europapark-2024/2.json` holds 225 cells
across 9 grids with 225 distinct ids, and every `make-grid` run mints an entirely fresh set.
No composite `(trip_slug, person, cell_id)` key is needed and none should be added — a person
name in a primary key would also make renaming a person a data migration.

**Why there are three columns beyond `cell_id`/`checked`/`updated_at`.** `temp-plan.md`
listed only those three. That set can't answer the one read the app actually performs —
"give me the checked state for this trip" — because with `cell_id` as the sole column the
server has no way to scope a query to a trip. The alternative (the client sends its 225 cell
ids as query params) blows past practical URL length limits at ~8KB and destroys the stable
cache key the `NetworkFirst` lane in §9 depends on. `trip_slug`/`grid_version`/`person` are
denormalized *scoping* columns, exactly as `docs/plan.md`'s original SQL sketch already had
them — they are not part of the key, and they are not cell text, so the "no `cells` table"
constraint holds. `person` isn't needed by any query today (cell ids are globally unique, so
the client maps cell → person from the grid JSON it already has); it's there because seeding
knows it for free and a debugging `SELECT` without it is miserable.

`grid_version` earns its place separately: without it, `GET`ing a slug returns rows from every
grid version ever generated for that slug, and those ids are disjoint from the live grid's, so
the client would silently download and discard them, growing forever.

**Table name**: `checked`, per `temp-plan.md`. `docs/plan.md`'s older sketch called it
`checked_cells` — that name is superseded.

### Migrations

`drizzle-kit generate` writes SQL into `db/migrations/`; **those files are committed.** With
no CI, the migration files are the only durable record that the schema in `db/schema.ts` and
the schema in Neon ever agreed. `drizzle-kit push` (schema diff applied directly, no file) is
fine for the fast local loop but must never be how production changes — `drizzle-kit migrate`
against the Neon URL is.

```ts
// drizzle.config.ts
import { defineConfig } from "drizzle-kit";

export default defineConfig({
  schema: "./db/schema.ts",
  out: "./db/migrations",
  dialect: "postgresql",
  dbCredentials: { url: process.env.DATABASE_URL! },
});
```

Neon note: run migrations against the **unpooled/direct** connection string
(`DATABASE_URL_UNPOOLED`), not the pooled one — DDL through a connection pooler in transaction
mode is a known source of confusing failures.

## 3. HTTP status contract

Defined once here and applied identically on every route, because the offline queue in §9
pattern-matches on these codes to decide "retry later" vs. "drop this write" vs. "the server
is right, adopt its value". A code picked ad hoc per route turns into a queue bug.

| Code | Meaning in this API | Used by |
| --- | --- | --- |
| `200 OK` | Request understood and satisfied. GET returns the map; PATCH returns the row as it now stands on the server. | GET, PATCH, both health routes |
| `400 Bad Request` | The request itself is malformed: missing/non-numeric `version`, unparseable JSON body, missing `id`, `checked` not a boolean, `updatedAt` not an ISO-8601 timestamp. **Client bug — never retryable.** | GET, PATCH |
| `404 Not Found` | The `cell_id` in a PATCH does not exist in the `checked` table. Means the grid was never seeded, or the client is holding a grid version the server has never seen. **Never retryable.** | PATCH |
| `405 Method Not Allowed` | Right path, wrong verb. Always sent with an `Allow` header. | all |
| `409 Conflict` | PATCH lost the optimistic-concurrency check — the server's row is newer than the basis timestamp the client sent. Body carries the current server row. **Not retryable; the client reconciles.** | PATCH |
| `500 Internal Server Error` | An unhandled exception in our code. Something is broken; the request was probably fine. | all |
| `503 Service Unavailable` | The database is unreachable or the query timed out. The request was valid; the dependency is down. **Retryable.** | GET, PATCH, `/api/health/db` |

Deliberate exclusions: **no `401`/`403` anywhere.** There is no auth guard, matching the rest
of the app — trip URLs are unauthenticated slugs today. Adding a guard later is no harder than
adding one now, so there is no cost to deferring it.

The 500/503 split is the one that matters most for the queue: 503 says "your write is fine,
try again", 500 says "we're broken". Both are treated as retryable by the queue (§9), but only
503 is *expected* during a Neon cold start or a scale-to-zero wake-up, so only 500 should ever
be surprising.

### Uniform error body

Every non-2xx response uses the same envelope, so the client parses one shape:

```json
{ "error": { "code": "CELL_NOT_FOUND", "message": "No checked row for cell id 5f3a…" } }
```

`409` is the one that carries extra fields — see §4.

```ts
// api/lib/responses.ts
export function json(body: unknown, status = 200, headers?: HeadersInit): Response {
  return new Response(JSON.stringify(body), {
    status,
    headers: { "content-type": "application/json", ...headers },
  });
}

export function apiError(status: number, code: string, message: string, extra?: object) {
  return json({ error: { code, message }, ...extra }, status);
}

export function methodNotAllowed(allow: string) {
  return apiError(405, "METHOD_NOT_ALLOWED", `Allowed: ${allow}`, undefined);
  // …with an Allow header — see json()'s third arg.
}
```

### Handler style

Use Vercel's **Web-standard handler signature** (named `GET`/`PATCH` exports taking a
`Request`, returning a `Response`), not the older `(req: VercelRequest, res: VercelResponse)`
style. Two concrete reasons, not taste:

1. One file can export both `GET` and `PATCH` without a hand-rolled `switch (req.method)`,
   and Vercel returns the `405` for unmatched verbs itself.
2. **It is directly unit-testable.** A handler is a plain async function from `Request` to
   `Response`, so an api test calls `GET(new Request("http://localhost/api/trips/x/checked?version=2"))`
   against the real test database with no HTTP server, no supertest, no port. That is what
   makes §7's test story cheap.

## 4. API routes

All routes are same-origin under `/api`. JSON on the wire is **camelCase** (`updatedAt`),
matching the TypeScript in this repo; Drizzle maps that to the snake_case columns. This is a
cosmetic deviation from `temp-plan.md`, which wrote the PATCH payload as `{ id, checked,
updated_at }` — recorded here as a visible decision rather than silent drift. The field is
`id` (not `cellId`) in the PATCH body, matching `GridCell.id` exactly.

### `GET /api/health`

`api/health.ts`. No database access at all — it answers the question "is the function
deployment alive and routing correctly", which is exactly what Phase 2's deploy checkpoint
needs to isolate from database problems.

```
200 → { "status": "ok", "service": "bingo-api", "time": "2026-08-28T12:00:00.000Z" }
```

Never returns 503. If this route is unreachable, the problem is Vercel routing or the build,
not Neon.

### `GET /api/health/db`

`api/health/db.ts`. Runs a real query against the `checked` table — `SELECT count(*)`, not
`SELECT 1` — so it proves connectivity *and* that migrations have actually been applied to
whatever database `DATABASE_URL` points at. `SELECT 1` would pass against an empty,
never-migrated database, which is precisely the failure mode this route exists to catch on a
first deploy.

```
200 → { "status": "ok", "rows": 225, "latencyMs": 41 }
503 → { "error": { "code": "DB_UNAVAILABLE", "message": "…" } }
```

`latencyMs` is worth having: a Neon cold start shows up here as a multi-second number, which
is normal and not a bug, and being able to see it beats guessing.

### `GET /api/trips/[slug]/checked?version=<n>`

`api/trips/[slug]/checked.ts`. Returns the whole trip's checked state in one request — the
client renders every person's grid on one page (`TripPage.tsx`), so there is no per-person
read to make.

`version` is **required**, not optional-defaulting-to-latest. The API has no opinion about
which grid version is live — `config/trips.json` does, and the client has already resolved it
via `loadTrip()` before it can render anything. Requiring it also gives the service worker a
cache key that changes the moment a grid is promoted (§9), the same property that makes the
existing `trip-data/` `CacheFirst` lane safe.

```
GET /api/trips/europapark-2024/checked?version=2

200 →
{
  "slug": "europapark-2024",
  "version": 2,
  "cells": {
    "9c1f…": { "checked": true,  "updatedAt": "2026-08-28T09:14:02.418Z" },
    "3ab7…": { "checked": false, "updatedAt": "2026-08-27T18:00:00.000Z" }
  }
}
```

**Every cell carries `updatedAt`, not just `checked`.** This is load-bearing: it's the basis
timestamp the client must send back on a PATCH (§4 below). A bare `Record<string, boolean>` —
which is what `src/lib/checked.ts` returns today — cannot support optimistic concurrency, so
the seam's return type has to widen in Phase 4. See §9.

Statuses:
- `200` — always, when the query succeeds, **including when there are zero rows** (`cells: {}`).
  An unknown slug and a not-yet-seeded slug are indistinguishable at the DB level, and the
  client only ever builds this URL from a slug `loadTrip()` already resolved, so a 404 here
  would add a failure mode that cannot occur while removing a legitimate one (a brand-new trip
  before its first seed).
- `400` — `version` missing or not a positive integer.
- `503` — database unreachable.

### `PATCH /api/checked`

`api/checked.ts`. Sets one cell's value, with optimistic concurrency.

Note the asymmetry with GET: PATCH is **not** nested under `/trips/:slug`. `cell_id` is
globally unique, so a slug in the URL would carry no information the body doesn't — it would
just create a second source of truth for "which trip is this" that the server would then have
to validate against the row, for no gain.

```
PATCH /api/checked
Content-Type: application/json

{ "id": "9c1f…", "checked": true, "updatedAt": "2026-08-28T09:14:02.418Z" }
```

`updatedAt` here is the client's **basis** timestamp — the value it last knew for that row,
from the GET response or from a previous PATCH's response. It is emphatically not "now". The
server is the sole authority on that clock.

Server logic:

```sql
UPDATE checked
   SET checked = $2, updated_at = NOW()
 WHERE cell_id = $1
   AND updated_at <= $3      -- $3 = the client's basis timestamp
RETURNING *;
```

- Row returned → `200`, body is the updated row.
- No row returned → the row either doesn't exist or the guard failed. Re-`SELECT` by `cell_id`
  to distinguish: absent → `404`; present → `409`.

```
200 →
{ "id": "9c1f…", "checked": true, "updatedAt": "2026-08-28T09:20:11.902Z" }

409 →
{
  "error": { "code": "STALE_WRITE", "message": "Row was modified at 2026-08-28T09:19:00.000Z" },
  "current": { "id": "9c1f…", "checked": false, "updatedAt": "2026-08-28T09:19:00.000Z" }
}
```

**The 409 body carries the full current server row** so the client can reconcile immediately
— show what is actually true — without a follow-up GET. That is the whole point of returning
it rather than a bare status.

Statuses: `200` on success · `400` malformed body (missing `id`, non-boolean `checked`,
unparseable `updatedAt`) · `404` unknown `cell_id` · `409` stale basis · `405` non-PATCH ·
`503` DB unreachable · `500` unhandled.

Use `<=` rather than `<` in the guard so that re-sending an identical write with an unchanged
basis timestamp succeeds (it's a no-op set to the same value) instead of 409-ing. The queue
drains at-least-once by design; a duplicate delivery must not look like a conflict.

## 5. Seeding

Folded into `make-grid`, per `temp-plan.md` — one command generates and seeds, so the second
step can't be forgotten. `data/createGrids.ts` currently ends by writing the JSON and printing
the `config/trips.json` line to edit; it gains a seed call after the write.

```ts
// data/seedGrid.ts
import { db } from "../db/client";
import { checked } from "../db/schema";
import type { Grid } from "../types/trip";

export async function seedGrid(
  slug: string,
  version: number,
  grids: Grid[],
  people: string[]
): Promise<number> {
  // grids[i] ↔ people[i] is positional and unenforced in the static-file world
  // (docs/plan.md flags this as pre-existing). Seeding writes that pairing into
  // the database, so assert it here rather than persisting a silent mismatch.
  if (grids.length !== people.length) {
    throw new Error(`Grid/people mismatch: ${grids.length} grids, ${people.length} people`);
  }

  const rows = grids.flatMap((grid, personIndex) =>
    grid.flat().map((cell) => {
      // grids/europapark-2024/1.json predates cell ids entirely (it's the
      // pre-backfill version — see docs/plan.md). Fail loudly rather than
      // inserting a null primary key.
      if (!cell.id) {
        throw new Error(`Cell without an id in ${slug} v${version} — grid predates cell ids?`);
      }
      return {
        cellId: cell.id,
        checked: false,
        tripSlug: slug,
        gridVersion: version,
        person: people[personIndex],
      };
    })
  );

  // Idempotent: safe to re-run after a partial failure. Cell ids are freshly
  // minted per make-grid run so conflicts should never actually occur — this
  // is a retry affordance, not a merge strategy.
  await db.insert(checked).values(rows).onConflictDoNothing();
  return rows.length;
}
```

`data/createGrids.ts` (existing code unchanged above this point — the `nextVersion`
computation, `getGrids({ data, characters, people, number: people.length })`, and the
`fs.writeFile`):

```ts
console.log(`Wrote grids/${slug}/${nextVersion}.json`);

try {
  const seeded = await seedGrid(slug, nextVersion, grids, people);
  console.log(`Seeded ${seeded} checked rows into ${dbLabel()}.`);
} catch (error) {
  console.error(`Grid file written, but seeding failed:`, error);
  console.error(`Re-run: npm run seed-grid -- ${slug} ${nextVersion}`);
  process.exitCode = 1;
}

console.log(`Set config/trips.json's "${slug}".currentVersion to ${nextVersion} to make it live.`);
```

**The separate `npm run seed-grid -- <slug> <version>` entry point is not optional
convenience — it is the only safe retry path.** Re-running `make-grid` after a failed seed does
*not* retry: `makeGrid()` is unseeded-random and never overwrites, so a second run produces a
*new numbered version with a completely different set of cell ids*. The grid file that was
already written would be orphaned, and you'd be seeding a grid nobody is looking at. `seedGridCli.ts`
reads the already-written `grids/<slug>/<version>.json` plus `data/<slug>/people.ts` and calls the
same `seedGrid()`.

**Which database does `make-grid` seed?** Whatever `DATABASE_URL` is when it runs — the same
env var the routes use. A grid destined for production must be seeded against the production
(Neon) URL, which means running `make-grid` with the production `DATABASE_URL` in the
environment. Print the target host in the "Seeded N rows" line (`dbLabel()` above — host only,
never the credentials) so it's impossible to seed dev and then wonder why production is empty.
This is a **human decision point at grid-generation time**, not something to infer.

Rows must exist before the API can serve them: `PATCH` on a missing `cell_id` returns `404`
and the frontend drops the write (§9). Seeding is not an optimization.

## 6. Local development

### `docker-compose.yml`

```yaml
services:
  postgres:
    image: postgres:17-alpine
    container_name: bingo-postgres
    restart: unless-stopped
    environment:
      POSTGRES_USER: bingo
      POSTGRES_PASSWORD: bingo
      POSTGRES_DB: bingo_dev
    ports:
      # 5433, not 5432 — a host-installed Postgres on the default port would
      # otherwise make `docker compose up` fail (or, worse, succeed while every
      # connection silently goes to the wrong server).
      - "5433:5432"
    volumes:
      - bingo-pgdata:/var/lib/postgresql/data
      - ./docker/init-test-db.sql:/docker-entrypoint-initdb.d/init-test-db.sql:ro
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U bingo -d bingo_dev"]
      interval: 5s
      timeout: 3s
      retries: 10

volumes:
  bingo-pgdata:
```

```sql
-- docker/init-test-db.sql
CREATE DATABASE bingo_test OWNER bingo;
```

**Gotcha**: files in `/docker-entrypoint-initdb.d/` run **only when the data volume is
empty**. If this file is added after the container has already initialised once, it is
silently ignored — you'd have to `docker compose down -v` (destroys dev data) or create the
database by hand:
`docker compose exec postgres psql -U bingo -d bingo_dev -c 'CREATE DATABASE bingo_test'`.

### Environment files

`.env.local` — **gitignored, never committed**:

```
DATABASE_URL=postgres://bingo:bingo@localhost:5433/bingo_dev
DB_DRIVER=pg
```

`.env.test` — **committed**. It contains only credentials for a throwaway local container that
is not reachable from anywhere; committing it means the test suite works after a clone with no
setup ritual beyond `docker compose up -d`:

```
TEST_DATABASE_URL=postgres://bingo:bingo@localhost:5433/bingo_test
DB_DRIVER=pg
```

⚠️ **`.gitignore` currently has no `.env` entries at all** (it lists only `.vercel`, `dist/`,
`node_modules/`). It must gain them before any env file exists, or `vercel env pull` — which
writes real production credentials into `.env.local` — will offer them up for commit:

```
.env*.local
```

### Commands

These do not exist yet — they're added to `package.json` in the phases below, and to
`CLAUDE.md`'s command table at the same time (the repo's rule is that CLAUDE.md's table is the
verified list, so it gets updated in the same commit as the script, never after).

| Task | Command |
| --- | --- |
| Start local Postgres | `npm run db:up` → `docker compose up -d --wait` |
| Stop it | `npm run db:down` → `docker compose down` |
| Reset it completely | `npm run db:reset` → `docker compose down -v && docker compose up -d --wait && npm run db:migrate` |
| Apply migrations (dev) | `npm run db:migrate` → `dotenv -e .env.local -- drizzle-kit migrate` |
| Generate a migration | `npm run db:generate` → `drizzle-kit generate` |
| Inspect data | `npm run db:studio` → `drizzle-kit studio` |
| Dev server **with** the API | `npm run dev:api` → `vercel dev` |
| Re-seed an existing grid | `npm run seed-grid -- <slug> <version>` |

**`npm run dev` (plain `vite`) does not serve `api/` at all** — Vite knows nothing about
Vercel Functions, so every `/api/*` fetch 404s and the app silently falls back to cached/empty
state, which looks exactly like being offline. `vercel dev` runs the Vite dev server *and* the
functions on one port with production routing semantics, so it's the command to use whenever
backend behaviour is in question. Plain `npm run dev` stays perfectly fine for pure
styling/layout work. (The alternative — a `server.proxy` entry in `vite.config.ts` pointing
`/api` at a separately-run process — was not chosen: it means maintaining a second dev-only
routing config that can drift from `vercel.json`.)

`--wait` on `docker compose up -d` matters: it blocks until the healthcheck passes, so
`db:reset` doesn't race the migration against a Postgres that hasn't finished starting.

### Two `vercel dev` gotchas hit and fixed during Phase 1 (not hypothetical — this happened)

Getting `vercel dev` actually working locally surfaced two real project-configuration
problems, neither of which is the `vercel.json` rewrite risk called out in §8 below — both
were more fundamental than that, and both are now fixed on the live Vercel project:

1. **The project's Root Directory was `dist`**, a leftover from the original "dragged
   `dist/` into Vercel by hand" setup this repo's CLAUDE.md describes. With Root Directory
   set to `dist`, Vercel treats that folder as the *entire* project — `vercel dev` searched
   for `api/` inside `dist/` and never found it, because `dist/` is pure static build output
   with no `api/` in it at all. This wasn't a rewrite problem (that would show up as a `200`
   of HTML); it was one level below that — Vercel didn't know `api/` existed, period. Fixed
   via `vercel project update <name> --auto-detect root-directory --output-directory dist`
   (clears the Root Directory override back to the repo root; Output Directory has to be set
   explicitly to `dist` at the same time, since without a Root Directory override Vercel's
   own guess defaults to `public` or `.`, neither of which is right for a Vite build).
2. **The Framework Preset was `Other`, not `Vite`, and didn't auto-detect** even after fixing
   Root Directory. With `Other`, Vercel's generic dev-command support doesn't pass
   `--port $PORT` to the dev command, so a plain `vite` binds its own default port (`5173`)
   instead of the port Vercel is listening for — `vercel dev` then fails with
   `Failed to detect a server running on port ...`. Fixed via
   `vercel project update <name> --framework vite`, after which Vercel runs
   `vite --port $PORT` itself and everything lines up.

A third thing worth knowing, not a bug but easy to get wrong: **`vercel dev`'s function
runtime reads local secrets from the linked Vercel project's own *Development*-scoped
environment variables (`vercel env add <NAME> development`), not from `.env.local`.**
`.env.local` is what the Vite dev *command* subprocess sees (so the frontend and
DB-access-free routes like `GET /api/health` work fine regardless) — but `api/` handlers
that touch the database failed with `Error: DATABASE_URL is not set` even though
`DATABASE_URL` was correctly sitting in `.env.local` the entire time, because the function
runtime pulls from the cloud-stored Development environment instead. `DATABASE_URL` and
`DB_DRIVER` were added there (pointing at the same local Docker Postgres connection string
`.env.local` already has — this is local-only data, it never reaches Vercel's actual
infrastructure, `vercel dev` just requires it to live in this particular place to be visible
to functions specifically).

## 7. Backend tests

Matching `docs/test-plan.md`'s stance: a few high-value tests through real code, minimal
mocking. The backend's version of that is **real handlers against a real database** — the
handlers are plain `Request → Response` functions (§3), so there is no server to start and
nothing to mock except nothing.

### Vitest project split

`vite.config.ts` currently sets one global `environment: "jsdom"` and one `setupFiles`. Backend
tests need `node` and a different setup file. In Vitest 4.1 (the installed version) that's
`test.projects` — **`environmentMatchGlobs` (Vitest ≤2) and `vitest.workspace.ts` (≤3) are both
removed**, so don't reach for either:

```ts
test: {
  projects: [
    {
      extends: true,
      test: {
        name: "web",
        environment: "jsdom",
        setupFiles: ["./vitest.setup.ts"],
        include: ["src/**/*.test.{ts,tsx}", "data/**/*.test.ts"],
      },
    },
    {
      extends: true,
      test: {
        name: "api",
        environment: "node",
        setupFiles: ["./api/test/setup.ts"],
        include: ["api/**/*.test.ts", "db/**/*.test.ts"],
      },
    },
  ],
}
```

`npm run test` (`vitest run`) still runs everything. The existing `data/**` tests stay in the
`web` project on jsdom — they're Node-context but jsdom doesn't bother them, and moving them is
churn for no benefit.

Escape hatch if the project split proves fiddly: a `// @vitest-environment node` docblock at
the top of a single test file. That's enough for the environment, but not for the per-project
`setupFiles`, which is why the split is the recommendation.

### Setup / teardown

```ts
// api/test/setup.ts
process.env.DATABASE_URL = process.env.TEST_DATABASE_URL;  // before db/client.ts is imported
process.env.DB_DRIVER = "pg";
```

- **`beforeAll` (once per run)**: apply migrations to `bingo_test` via Drizzle's programmatic
  migrator (`migrate(db, { migrationsFolder: "db/migrations" })`). This exercises the committed
  migration files, so a migration that doesn't apply cleanly fails the suite — the closest this
  project gets to the one thing CI would have given us.
- **`beforeEach`**: `TRUNCATE checked` — fast, and leaves every test starting from a known-empty
  table. Not `DROP`/recreate: truncate is milliseconds, re-migrating per test is not.
- **No teardown of the container.** It's a long-lived dev container, and the test *database* is
  separate from the dev one, so a test run can never corrupt local dev data.

**The test DB is a separate database, not a separate schema**, on the same container. A
separate `search_path` schema would require every query and the migrator to be schema-aware;
a separate database is one changed connection string and total isolation.

### What to actually test

1. **`GET /api/trips/[slug]/checked`** — seed rows directly via Drizzle, call the handler,
   assert the `cells` map shape including `updatedAt`; assert `200` + `{}` for an unknown slug;
   assert `400` for a missing/garbage `version`; assert rows from a *different* `grid_version`
   of the same slug are excluded (the regression guard for §2's `grid_version` reasoning).
2. **`PATCH /api/checked`** — the full status contract, one test per row of §3's table:
   `200` happy path (and that `updatedAt` actually advanced), `409` with a stale basis
   (asserting the `current` body shape, since the frontend queue parses it), `404` unknown
   cell, `400` malformed body, and the duplicate-delivery case (same write twice with the same
   basis → `200` both times, not `409`).
3. **`seedGrid()`** — against real generated grids from `getGrids()`: correct row count
   (`people.length × 25`), correct person↔grid pairing, throws on a grid/people length
   mismatch, throws on an id-less cell, and is idempotent when run twice.
4. **`GET /api/health/db`** — `200` against the live test DB. The `503` path is deliberately
   *not* tested; faking an unreachable database is all mock and no signal.

Deliberately not tested: `GET /api/health` (it returns a literal), and the Drizzle query
builder itself.

### The `vercel.json` rewrite — already fixed, and for a bigger reason than expected

`vercel.json` originally had `{"source": "/(.*)", "destination": "/index.html"}` — the SPA
catch-all. The plan was to verify this didn't swallow `/api/*` on first deploy (Vercel's
documented routing order checks the filesystem *before* rewrites, so it was expected to be
fine in production) — but this got caught earlier than planned, during Phase 1's own local
`vercel dev` testing, and for a more fundamental reason than the one anticipated.

**`vercel dev`'s proxy to the framework dev server does not check real files before applying
a rewrite the way production's static hosting does.** With the original blanket
`/(.*)` pattern, *every* request got rewritten to `/index.html` — including Vite's own
dev-only module paths like `/src/main.tsx`, which don't exist as real files (Vite serves them
transformed, on the fly). The browser would request `/src/main.tsx`, get back `index.html`'s
HTML instead, and Vite's import-analysis plugin would then fail trying to parse that HTML as
the JS module it thought it was loading — `Failed to parse source for import analysis because
the content contains invalid JS syntax`. This has nothing to do with `/api/*` specifically; it
broke the frontend itself under `vercel dev`.

Fixed to exclude both `/api/*` **and anything that looks like a real file** (has a `.` in the
path), not just the API prefix originally planned:

```json
{ "source": "/((?!api/)(?!.*\\.).*)", "destination": "/index.html" }
```

This is a strictly more defensive pattern than the original, not just a fix for the same
problem: in production, `dist/`'s built assets all have extensions and would have been caught
by the filesystem check anyway — but the same pattern also now correctly falls through for
`/src/main.tsx`-style dev-only paths under `vercel dev`, which never touch the filesystem
check at all locally, only in a real deployment.

The `no-cache` headers already in `vercel.json` for `/sw.js` and `/registerSW.js` stay as they
are — unrelated, and load-bearing for `registerType: "autoUpdate"`.

### Repo config that has to move with this

- **`.gitignore`** — add `.env.local` and `.env*.local` (see §6). Do this *first*, before any
  env file is created.
- **`tsconfig`** — `npm run build` runs `tsc -b`, which only typechecks files reachable from
  the referenced projects. `api/` and `db/` are in neither today, so backend type errors would
  not fail the build. Add a `tsconfig.api.json` (`types: ["node"]`, `lib: ["ES2023"]`,
  `include: ["api", "db"]`) and reference it from `tsconfig.json`. `@types/node` v26 declares
  the global `Request`/`Response`/`fetch` types the Web-standard handlers need, so no `DOM` lib
  is required — if they come up as missing, that's the thing to check, not a reason to pull in
  `DOM`. Watch for "file is in multiple projects" if `db/` ends up in both `tsconfig.node.json`
  and `tsconfig.api.json`; keep it in exactly one `include`.
- **`npm run lint`** is `eslint src --ext ts,tsx` — it does not touch `api/`, `db/`, or `data/`.
  Widen it to `eslint src api db --ext ts,tsx` so backend code is actually linted. `.eslintrc.cjs`
  sets `env: { browser: true }` globally; backend files need `node: true`, which is cleanest as
  an `overrides` entry for `api/**` and `db/**` rather than turning both on everywhere.
- **`api/` is invisible to Vite's build** (nothing in `index.html`'s graph imports it), so there
  is no bundling interaction and no `globIgnores` change needed for it.

## 9. Frontend integration (Phase 4)

The design below is settled, not a menu. The governing idea: **there is exactly one write
path.** Every save goes through the queue, online or offline. There is no "if online, PATCH
directly; else queue" branch — which means the 409/404/503 handling is written once instead of
twice, and the offline path is exercised on every single save rather than only in the rare
case, so it can't rot.

### What changes in the existing seam

`src/lib/checked.ts`'s two functions were built for exactly this swap (`docs/plan.md`: "the
seam is what's meant to survive, not necessarily the MVP's internals"). Two of its assumptions
do have to change:

1. **The return type widens.** `Record<string, boolean>` cannot carry the `updatedAt` basis
   timestamp the PATCH contract requires. It becomes a map of `{ checked, updatedAt }`.
2. **The `person` parameter goes away.** `getChecked(tripSlug, person)` was per-person because
   localStorage keys were. The API is trip-scoped, and cell ids are globally unique, so `person`
   carries no information — `CheckedContext` maps cell → person from the grid it already has.
   Keeping an unused parameter for signature compatibility would be worse than the two-line
   change at the call site in `Tile.tsx`.

```ts
// src/lib/checked.ts — Phase 4
export interface CheckedCell {
  checked: boolean;
  updatedAt: string; // ISO-8601, server-authoritative
}
export type CheckedMap = Record<string, CheckedCell>;

/** GET /api/trips/:slug/checked?version=n. Throws on network failure; the
 *  service worker's NetworkFirst lane silently serves the cached response
 *  first, so a throw here means "offline AND never loaded this trip before". */
export async function fetchChecked(tripSlug: string, version: number): Promise<CheckedMap>;

/** The only write entry point. Writes to the persisted queue synchronously,
 *  then fires a drain. Never throws — a failed drain just leaves work queued. */
export async function saveChecked(
  tripSlug: string,
  cellId: string,
  value: boolean,
  basisUpdatedAt: string
): Promise<void>;
```

`CheckedProvider`'s public surface (`isChecked`, `updateChecked`) is unchanged apart from
dropping `person`, so `Grid.tsx` and `Tile.tsx`'s Save button keep working as-is. `TripPage.tsx`
passes `version` (from the same `TripConfig` `loadTrip` already read) into the provider — it's
currently thrown away by `loadTrip`, so `LoadedTrip` in `types/trip.ts` gains a `version:
number` field.

### The queue

```ts
// src/lib/checkedQueue.ts
export interface QueuedWrite {
  cellId: string;
  checked: boolean;
  basisUpdatedAt: string;  // what the client knew when the edit was made
  enqueuedAt: string;      // identity token — see "the in-flight re-toggle" below
}

/** Keyed by cellId, NOT an append log. Toggling the same cell twice while
 *  offline replaces the pending entry rather than queueing two replays —
 *  only the latest value per cell can possibly matter. */
export type CheckedQueue = Record<string, QueuedWrite>;

const QUEUE_KEY_PREFIX = "bingo:checked:queue";  // → bingo:checked:queue:<tripSlug>
```

`localStorage`, matching the repo-wide `bingo:` prefix convention (`bingo:tintsEnabled`,
`bingo:checked:<slug>:<person>`). **In-memory would defeat the entire point** — a reload while
offline is the single most likely thing to happen to a pending write, and it's also drain
trigger #2.

```ts
export function readQueue(tripSlug: string): CheckedQueue;
export function enqueue(tripSlug: string, write: QueuedWrite): CheckedQueue;
export function removeIfUnchanged(tripSlug: string, write: QueuedWrite): CheckedQueue;
export function drain(tripSlug: string, onServerRow: (row: CheckedCell & { id: string }) => void): Promise<void>;
```

### Drain triggers — exactly three

1. **Immediately after enqueueing.** Drains the *whole* queue, not just the new entry — if it
   fails, everything simply stays queued for the next trigger.
2. **On mount** (`CheckedProvider`'s effect), after the initial GET.
3. **On the browser's `online` event** (`window.addEventListener("online", …)`, removed on
   unmount).

**No periodic polling and no manual "Resync" button.** This was a deliberate simplification
over an earlier polling idea: the status indicator below makes a stuck queue *visible*, and the
obvious human response — reload — is itself trigger #2. That covers the same gap without an
always-on timer.

### Drain behaviour, per status code

Entries are PATCHed **sequentially**, not `Promise.all` — the queue is at most a handful of
entries, sequential keeps conflict handling linear, and it avoids a burst of parallel requests
at a server that may have just cold-started.

| Response | Action |
| --- | --- |
| `200` | Apply the returned row to React state (functional update). Remove the entry (see below). |
| `409` | The server is right. Apply `body.current` to React state — the local edit is discarded. Remove the entry. Last-writer-in-server-time wins; this is exactly why the 409 body carries the row. |
| `400` / `404` | Unretryable. Remove the entry and `console.warn` — the tile reverts to server truth on the next GET. A `404` specifically means the grid wasn't seeded; leaving it queued would retry forever. |
| `500` / `503` / network error / timeout | **Abort the rest of the drain**, leave everything queued. No point walking the remaining entries against a server that just failed. |

A module-level `draining` flag guards against triggers 1, 2, and 3 firing at once and
double-sending.

### The two concurrency disciplines

**React state**: always the functional/updater form.

```ts
setCells((current) => ({ ...current, [cellId]: serverRow }));
```

Never `setCells({ ...cells, [cellId]: … })` — drain responses land close together and out of
order, and the closed-over `cells` will be stale.

**localStorage**: any read-modify-write must be **synchronous, with no `await` between the read
and the write**.

```ts
// Correct — atomic with respect to any other JS on this thread.
const queue = readQueue(slug);
delete queue[cellId];
localStorage.setItem(key, JSON.stringify(queue));

// Wrong — another drain can read, modify and write in the gap, and its write is lost.
const queue = readQueue(slug);
await patch(...);
delete queue[cellId];
localStorage.setItem(key, JSON.stringify(queue));
```

**The in-flight re-toggle**, which is why `QueuedWrite` carries `enqueuedAt`: if the user
toggles a cell again while its PATCH is airborne, the queue entry for that `cellId` now holds a
*newer* value. Blindly deleting on `200` would silently drop it. `removeIfUnchanged` compares
`enqueuedAt` and only deletes when the entry is still the one that was sent.

### Reconciliation on load

`CheckedProvider`'s mount effect:

1. `fetchChecked(slug, version)` → the last-good server state (live, or the service worker's
   cached response if offline — see the caching lane below).
2. Replay the persisted queue's pending values **on top** of that.
3. Set state from the merge, then drain.

The queue is never the source of truth for anything except the cells it is currently
overriding. If the GET fails outright *and* there's no cached response (never visited this trip
online), the trip renders unchecked — the same state as a fresh device, which is honest.

### No online/offline gate

There is deliberately **no boolean that decides whether calls fire**. Reads and writes both
always attempt and degrade gracefully: writes stay queued, reads fall back to the service
worker's cache. `navigator.onLine` is unreliable (it reports "connected to a network", not
"the internet works"), and a gate would add a state that can be wrong. The
originally-envisioned "is the API live" health-check hook is downgraded from a gate to a pure
UX signal — `/api/health/db` is for humans and for the Phase 2 deploy checkpoint, not for
control flow.

### Status indicator

`src/components/QueueStatus.tsx` — conditionally rendered, fixed bottom-right, visible only
while the queue is non-empty:

> ⏳ 3 updates queued…

The count is **derived from the queue's size at render time**, never tracked in a separate
counter that can drift. This one element is what replaces both polling and a manual resync
button: if something is stuck the user sees it, and reloading — the obvious response — is
already trigger #2. Style it with existing semantic tokens (`bg-surface`/`text-ink`), not a
raw `bg-[#hex]`, per CLAUDE.md.

### The third caching lane

`vite.config.ts` has two lanes today: the precached app shell, and `CacheFirst` runtime caching
for `trip-data/*.js`. **Neither changes** — grid content stays file-based, and `CacheFirst` is
still correct there because a promoted grid is a new numbered file, so a `trip-data/` URL's
content genuinely cannot change.

The checked-state GET needs a **third lane, `NetworkFirst`** — the opposite policy, because
this URL's content *does* change and freshness is the point:

```ts
runtimeCaching: [
  { /* … existing trip-data CacheFirst rule, unchanged … */ },
  {
    // Checked state is mutable, unlike trip-data — so NetworkFirst, not
    // CacheFirst: try the network for freshness, fall back to the last good
    // response when it fails. This is what makes "the state as of the last
    // time the app loaded online" available offline.
    urlPattern: ({ url }: { url: URL }) =>
      url.pathname.startsWith("/api/trips/") && url.pathname.endsWith("/checked"),
    method: "GET",
    handler: "NetworkFirst",
    options: {
      cacheName: "checked-state",
      // Flaky venue wifi hangs rather than failing fast; without this the app
      // waits on a dead socket instead of rendering cached state.
      networkTimeoutSeconds: 5,
      expiration: { maxEntries: 20 },
      // Never cache an error response as if it were state.
      cacheableResponse: { statuses: [200] },
    },
  },
]
```

Notes on this lane:
- Workbox only handles `GET`. `PATCH /api/checked` is never intercepted or cached, which is
  correct — the offline queue is the write-side story, not the service worker.
- The `?version=n` query string is part of the cache key by default, so promoting a grid
  naturally starts a fresh cache entry rather than serving the previous version's state.
- `navigateFallback: "/index.html"` only applies to `mode: "navigate"` requests, so a `fetch()`
  to `/api/...` is not affected. Adding `navigateFallbackDenylist: [/^\/api\//]` costs nothing
  and removes the question permanently.
- Per `docs/test-plan.md`, service worker config is **not unit-testable** — verify this lane
  with `docs/visual-verification.md`'s recipe: load online, go genuinely offline (disconnect,
  not throttle), hard-reload, confirm checked state still renders.

### Tests for Phase 4

Following `docs/test-plan.md`'s existing direction: use **`msw`** to intercept `fetch` at the
network layer rather than mocking `fetchChecked`/`saveChecked` themselves, so the real request
construction and response parsing are exercised and only the HTTP round-trip is faked.
`src/lib/checked.test.ts`'s existing *assertions* (empty state, round-tripping a value) largely
survive; only the setup changes. New targets:

- Queue convergence: a sequence of offline saves, drained in any order, lands on the correct
  final value per cell.
- The in-flight re-toggle: a second save while the first is in flight is not lost.
- Each status-code branch of the drain table above, driven by `msw` responses.
- `TripPage.test.tsx` (the existing integration test) should keep passing with an `msw` handler
  swapped in for its localStorage assertions — it goes *through* the seam, not around it.
